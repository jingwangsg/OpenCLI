# Browser blocker SOP

Use this when an adapter receives a CAPTCHA, a block page, or HTTP 403/429/432. The objective is to recover the **real requested page and data**, then retry the command. A successful click, HTTP 200 from a homepage, or a dismissed dialog is not enough.

1. **Record the failure.** Read the retained trace summary, failed network status, final page state, and screenshot. Note the exact host/path and whether the page offers an interactive verification control. Check `opencli doctor` and `opencli profile list`; choose one connected, persistent browser profile and pass `--profile <alias>` on every follow-up call.
2. **Locate the boundary with normal browser navigation.** In a named `opencli browser` session on that profile, open the site's homepage, then follow its own visible navigation to the requested section. Wait for the relevant result selector, text, or request event and read `state` after each navigation; fixed sleeps do not establish readiness. If the site provides a regional or language link, try the one matching the user's market. Test whether the homepage, section page, and exact query fail at different points. Do not repeatedly fire the blocked adapter during this inspection.
3. **Use available page controls.** If a CAPTCHA, sign-in, or verification UI is visible, operate its normal controls through `opencli browser` and re-read the resulting page. Let the user complete any step that requires their credentials or personal authentication in that same profile. Preserve the site session (`--site-session persistent` for browser-backed adapters) when reusing a completed login or challenge. Confirm that the requested result cards or data load before calling the access problem resolved.
4. **Resume the adapter only after access works.** Run one exact query through the working browser path and profile. If the browser displays valid data but the adapter still fails, compare its navigation/session assumptions and parser against that page, make a focused adapter fix, then run the command and fixture again. Record a durable working entry path in the site's notes.
5. **Report an unresolved block precisely.** If the homepage works but the target path still returns a block without usable controls, state which paths and hosts were tried and the observed status/page text. Give a concrete resume condition, such as the target result page loading in the connected browser. Continue independent work where possible; do not silently replace a user-required source or invent prices.

Keep retries tied to a changed state or a distinct site-provided entry path. Repeating the same blocked URL without a new observation adds no evidence.
